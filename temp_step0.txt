# PHASE 1 — Establish the Variant Domain Contract

**Priority: 🔴 CRITICAL**

Before touching UI, we need to formally define what a valid variant means.

The current schema already establishes `product_variants` as the purchasable atom and stores `option_combination` as JSONB.

The problem isn't that the schema is fundamentally wrong.

The problem is that the application hasn't finished enforcing the meaning of that schema.

## Target invariant

For a product:

```text
T-Shirt

Color:
  Red
  Blue

Size:
  Small
  Medium
  Large
```

the valid variant set is:

```text
Red / Small
Red / Medium
Red / Large
Blue / Small
Blue / Medium
Blue / Large
```

Each variant must have:

```text
variant.id
product_id
option_combination
sku
status
price override
image
inventory
```

and every combination must be unique.

### We need to establish:

* What constitutes a combination?
* Are option IDs stored in `option_combination`, or value IDs?
* How are combinations normalized?
* How are combinations compared?
* What happens when an option value is deleted?
* Can a variant exist without options?
* When is `{}` valid?
* How does a simple product differ from a configurable product?
* What is the canonical/default variant?

### Important decision

I recommend:

> **Simple products remain a single default variant with `{}` as their combination.**

That preserves the existing architecture.

A configurable product then has one or more actual combinations.

# PHASE 2 — Fix Variant Creation Lifecycle

**Priority: 🔴 CRITICAL**

This is where the current implementation has the largest functional hole.

`createProductAdmin()` creates the initial product, then creates **one default variant**, then creates its inventory record.

The service also exposes functions for:

* creating option groups
* adding option values
* deleting option groups
* deleting option values
* updating variant SKU/price

but there is no complete variant-generation lifecycle.

## Target workflow

Admin:

```text
Create Product
      ↓
Add Size
      ↓
Add S / M / L
      ↓
Add Color
      ↓
Add Red / Blue
      ↓
Generate Variants
```

System generates:

```text
S + Red
S + Blue
M + Red
M + Blue
L + Red
L + Blue
```

Then each receives:

```text
SKU
price
status
inventory
image
```

## Required behavior

If an admin adds another value later:

```text
Color:
Red
Blue
Green
```

the system must intelligently add:

```text
S + Green
M + Green
L + Green
```

without duplicating existing variants.

Likewise, if an option value is removed, the system must determine whether the corresponding variants:

* become inactive
* become archived
* are deleted
* or are retained historically.

**We should not silently delete variants that may already have order history.**

# PHASE 3 — Make Variant + Inventory Atomic

**Priority: 🔴 CRITICAL**

This is the root of the checkout failure.

The current inventory service deliberately treats a missing inventory record as untracked stock in `checkAvailableStock()`:

```text
if (!inv || !inv.track_inventory) return 9999;
```

but `reserveInventoryForCheckout()` subsequently requires the inventory record and throws if it doesn't exist.

That creates:

```text
PDP
 ↓
"No inventory record"
 ↓
treated as available
 ↓
Add to Cart
 ↓
Checkout
 ↓
"No inventory record"
 ↓
FAIL
```

That must disappear.

## Target rule

We need exactly one interpretation.

I recommend:

> **Every purchasable variant receives an inventory record.**

Even if inventory tracking is disabled:

```text
inventory_records
track_inventory = false
```

The record still exists.

That makes:

```text
variant → inventory
```

a stable invariant.

The existing database already models inventory as 1-to-1 with variants through `variant_id UNIQUE`.

So we can reinforce the existing architecture rather than inventing another inventory model.

---

# PHASE 4 — Make Inventory Reservation Transaction-Safe

**Priority: 🔴 CRITICAL**

The current reservation logic does:

```text
check stock
 ↓
fetch inventory
 ↓
create reservation
```

for every line sequentially.

That is vulnerable to concurrency.

Two customers can theoretically see the same available quantity before either reservation is committed.

## Target

Reservation needs to be authoritative at the database boundary.

Something along the lines of:

```text
reserve_inventory(checkout_session, [
  variant A × 2,
  variant B × 1
])
```

inside one transactional operation.

The database should atomically:

1. resolve inventory
2. expire stale reservations if necessary
3. calculate available quantity
4. lock the relevant inventory rows
5. verify stock
6. create reservations
7. update reserved quantity
8. return reservation IDs.

This is much safer than application-side:

```text
SELECT
INSERT
SELECT
INSERT
```


Never:

# PHASE 6 — Variant Availability Matrix

**Priority: 🔴 CRITICAL**

The UI needs to understand combinations, not just individual values.

Example:

```text
             Small    Medium    Large

Red           ✓         ✓         ✗
```


The UI should not merely ask:

# PHASE 7 — Fix Variant Pricing

**Priority: 🔴 CRITICAL**

We currently have:

```text
variant.price_override ?? product.base_price
```

in important paths.

That means `sale_price` can be bypassed.

We need one canonical pricing resolver.

For example:

```text
resolveVariantPrice(product, variant)
```

with an explicitly chosen precedence.

Likely:

```text
variant.price_override
        ↓
product.sale_price
        ↓
product.base_price
```

if that matches the intended business rules.

Then **every** surface uses that resolver:

```text
PDP
Cart
Checkout
Payment
Order
Email
JSON-LD
Admin preview
```

No component should calculate variant price independently.

## What I consider the immediate blockers

If we're going to work on this together incrementally, I would mark these as our **first five implementation checkpoints**:

### 🔴 1. Variant + inventory invariant

Every active purchasable variant has exactly one inventory record.

### 🔴 2. Variant combination engine

`Size × Color × ...` produces deterministic, unique variants.

### 🔴 3. Canonical variant resolver

Every UI selection maps to exactly one variant or no variant.

### 🔴 4. Atomic multi-variant checkout

Multiple variants from the same product can reserve, pay and become order lines correctly.

### 🔴 5. Canonical variant pricing

One pricing resolver feeds PDP → cart → checkout → payment → order → SEO.

Once those five are solid, **then** we build the SEO layer on top of them.
